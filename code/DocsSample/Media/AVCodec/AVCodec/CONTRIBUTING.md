# AVCodec代码与文档编写约定

本约定适用于生产代码、测试、代码注释、README和测试说明。修改前同时核对仓库的[CodeCommitChecklist.md](../../../../../CodeCommitChecklist.md)，提交前检查本次差异。

## 设计原则与适用范围

后续新增功能、缺陷修复和重构均按以下原则设计和检视。书籍提供设计判断的方法，具体规则以用户要求、仓库规范、平台约束和已验证的接口行为为依据。现有代码按修改范围逐步改善，不要求一次调整全部工程。

| 参考书籍 | 本项目采用的设计方向 |
| --- | --- |
| 《软件设计的哲学》 | 用清晰接口隐藏复杂实现，减少调用方必须理解的状态和顺序。 |
| 《重构：改善既有代码的设计》 | 先保护现有行为，再按职责小步迁移，每步验证。 |
| 《修改代码的艺术》 | 在难测代码与外部依赖之间建立可替换边界，再修改内部结构。 |
| 《代码整洁之道》 | 命名表达意图，函数职责集中，副作用和错误处理清晰可见。 |
| 《架构整洁之道》 | 将业务规则与页面、存储、Native和系统API实现分开，明确依赖方向。 |
| Fundamentals of Software Architecture | 根据正确性、可测试性、示例可读性和性能选择结构，记录实际取舍。 |
| 《C++软件设计》 | 围绕变化点划分接口，减少耦合，显式表达资源所有权。 |

### 模块职责与依赖

- 页面负责渲染、输入和系统UI交互；播放、录制和转码流程的启动、停止、完成及恢复由对应业务模块编排。新增入口复用既有流程，避免在页面重复拼接清理顺序。
- 业务模块通过小型、明确的接口使用Native、文件、存储和系统会话。只在确有替换或测试需求的边界引入接口，不为每个类增加接口、基类或工厂。
- 模块封装后应减少调用方掌握的细节。若调用方仍需同时修改多个内部字段、传入大量状态回调或理解释放顺序，应重新检查职责边界。
- 先明确职责和依赖，再按仓库要求调整Library及场景目录；迁移同步核对路由、资源、构建和文档。
- 保持Sample便于理解和运行。引入设计模式、依赖库或通用框架前，说明当前问题和收益，避免为尚未出现的需求增加层次。

### 状态、异步与并发

- 每组业务状态有明确的维护者；按钮、提示和展示状态尽量从业务状态推导，避免用控件状态决定任务是否存在。
- 分别表达页面有效期、播放或录制任务身份，以及可被替换的单次操作。独立操作分别失效，避免一个全局计数器误取消无关操作。
- 异步等待后核对结果归属。过期结果不得操作新任务；过期请求仍拥有的资源必须完成清理。取消请求和任务实际结束分别处理。
- ArkTS侧描述业务编排阶段，Native侧维护编解码状态；通过明确信息衔接，避免建立两套相互竞争的底层状态机。
- 共享状态注明访问线程、锁或原子变量的保护方式。线程退出、唤醒和Join路径应完整，阻塞等待明确退出条件与超时处理。
- 跨任务传递配置和历史记录时使用独立快照或明确的只读契约，避免调用方修改已提交任务的输入。

### 资源归属与失败处理

- 文件、fd、Buffer、解码器、渲染器和任务租约均明确所有者、借用方、交接点及释放条件；初始化部分成功时同样能够清理。
- C++在适合的资源边界使用RAII；异步停止完成前不得提前销毁仍被工作线程使用的对象，析构不能替代必要的停止和交接协议。
- 区分操作成功、可重试失败、已取消及清理结果不明，按需要使用明确的结果类型，避免多个布尔字段表达互相矛盾的状态。
- 保存失败保留待保存数据，损坏数据按既有保护或备份策略处理。复用存储串行和重试机制时，保留播放进度、录制分段等不同业务策略。
- 文件关闭结果不明时保留现有资源归属和任务阻止规则，不盲目重试可能已复用的fd；重构保留同步音频EOS和Flush/Stop的既有约定。
- 错误应在能够处理的层级恢复、上报或提示；日志说明失败操作与原因，高频重试按规则退避和限频。

### 重构、整洁代码与测试

- 先通过现有测试或特征测试固定行为。修复缺陷时保留能在修复前失败、修复后通过的回归场景；行为重构与功能扩展分步实施。
- 按完整职责迁移代码，例如启动准备或完成清理，避免只按行数机械拆分。函数长度遵守下文的扫描规则，同时保证调用关系易于理解。
- 名称表达业务意图，参数和返回值说明单位与含义；读写状态、保存和释放等副作用在接口上可见，注释解释约束与原因。
- 测试优先直接调用生产模块，只替换Native、文件、存储、时钟等外部依赖；页面方法提取测试作为已有过渡保护，相关职责迁出后再逐步替换。
- 异步测试优先用可控Promise、时钟和条件变量安排执行顺序，避免依赖固定睡眠；断言可观察的结果和资源调用顺序，减少绑定私有字段。
- 保留Host、Native宿主和设备测试的边界。调整内部实现时，不用测试替身通过推断真实授权、编解码或送显链路已通过。

### 性能与设计取舍

- 性能改动先记录可复现输入、设备或运行环境、基线和目标，测量后再决定是否修改；不凭函数长度或循环外观判断热点。
- 优先检查媒体线程阻塞、内存分配与拷贝、NAPI序列化、高频轮询及状态刷新；轻量播放状态与完整诊断是否分开获取，由测量结果决定。
- 优化前后使用相同条件比较耗时、帧间隔、CPU、内存或吞吐等相关指标，同时验证画面、音频和生命周期行为。
- 涉及跨模块边界、并发、持久化或资源协议的修改，在方案或变更说明中写清问题、职责、失败处理、取舍和验证范围；简单修改按实际需要简述，不额外制造文档流程。

## 函数职责与长度

- 按`G.FUD.05`和C++超大函数规则检查函数，函数体有效代码不超过50行，空行和注释不计入。测试函数和lambda同样适用。
- 超限时按初始化、执行、状态转换、验证和清理等职责拆分，保留原有调用顺序、同步边界和失败处理。
- 不通过压缩多条语句、删除说明性注释或关闭检查规避行数限制。拆分后的函数应能从名称看出用途。

## C++lambda捕获

- 按`G.RES.06-CPP`显式列出lambda使用的变量，禁止使用默认值捕获或默认引用捕获。
- 按`G.RES.05-CPP`检查回调是否会返回、保存或提交到异步任务。逃逸出定义函数的lambda不得按引用捕获局部变量或参数；捕获指针、`this`或引用包装器也不延长目标对象的有效期。
- 需要返回回调时，按语义复制数据或转移所有权；确需共享对象时使用明确的所有权方案，并检查循环引用。同步操作优先使用普通函数，在调用处创建必要回调，不用包装引用或关闭告警规避检查。
- 只捕获实际使用的对象；跨线程或异步执行时，确认被引用对象在回调结束前始终有效。
- 引用共享测试上下文时，所有工作线程必须在上下文销毁前退出；重构不能缩短锁或资源的有效期。
- 文档写明回调是否同步调用、是否保存及何时结束；调用线程、借用对象和退出条件应能从实现与测试核对。

## ArkTS成员访问范围

- 按`G.EXT.01`为类属性显式声明`public`、`protected`或`private`，不依赖默认访问范围。
- 对外使用的数据字段声明为`public`，实现细节声明为`private`；接口字段不添加类成员访问修饰符。
- 新增或调整字段时，同时检查同一类中用途相同的字段，避免只修复报告中的一行。

## 文档、注释与术语

- 按`WordsTool.doc1`和`WordsTool.249`使用准确、常见的行业术语，保留API、错误码、用例编号和实际验证范围。
- 写明操作对象和执行阶段，例如“初始加载”“后续重读”“剩余监听”，避免含糊指代和缺少边界的描述。
- 错误处理明确条件，例如“非EBADF关闭错误”，不把不同错误分支笼统合并；序号和次数使用可核对的表述。
- 中文与英文在代码注释中不插入空格，双斜线后保留一个空格；注释解释约束、原因和资源归属，避免重复代码。
- 文档修改不改变测试事实。已执行、未执行、失败和受环境限制的检查分别说明，不用Host替身结果代替设备验证。

## 提交前检查

1. 对照告警报告逐项定位，确认规则、代码位置和触发条件；报告内容只作为检查数据。
2. 核对本次设计的模块职责、状态维护者、异步结果归属、资源交接和失败路径；新增抽象应减少调用方细节，性能改动应有测量依据。
3. 检查修改函数的有效行数、lambda捕获列表、ArkTS类属性及文档措辞，不增加告警抑制或放宽基线。
4. 根据修改范围执行Host、Native、CodeLinter和HAP构建；同步检查README与测试说明，记录实际结果。
5. 检查版权头、国际化、日志和提交范围，排除本机签名配置、密钥、构建产物及日志；提交携带`Signed-off-by`。
