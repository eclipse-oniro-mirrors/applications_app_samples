# Audio 测试说明

> 本说明面向 `Audio`（OpenHarmony 音频能力综合示例）工程，用于说明本工程 ohosTest 自动化测试的设计思路、覆盖维度、充分性依据与后续扩展方向。

## 1. 文档目标

本文档用于说明 `Audio` 自动化测试的分层结构、用例组织、覆盖重点与质量门禁。文档聚焦“为什么这样设计测试”和“当前测试能证明什么”，用于辅助代码评审、测试审计和后续扩展。

当前测试代码位于 `entry/src/ohosTest/ets/test/`，由 `List.test.ets` 统一注册 **24 个测试套件、218 条用例**，测试代码约 **5,945 行**（有效代码行约 **3,392 行**），另有 `shared/AudioDriver.ets`（UiTest 驱动与资源/导航辅助）。

## 2. 测试设计原则

### 2.1 分层设计

测试基于 Hypium + UiTest 框架（入口 `List.test.ets`，运行器 `OpenHarmonyTestRunner`，测试承载页 `TestAbility`），按以下层次拆分：

- **基础能力层**：覆盖 `EntryAbility` 拉起与麦克风授权，首页七个入口卡片的可见性与跳转。
- **页面交互层**：覆盖发声设备、音频焦点、音效管理（预置/实时）、音频录制（普通/实时/并行）、音量面板、空间音频、卡拉 OK 的控件存在、状态切换与选择回显。
- **录制链路层**：覆盖采集器三标签页切换、开始/暂停/继续/停止的状态机与计时格式。
- **资源与国际化层**：通过 `resourceManager` 校验页面标题、内容类型、流用途、音效、按钮、设备类型等资源已正确接入。
- **稳定性与重入层**：覆盖页面“打开→返回→再打开”、跨页顺序返回、播放态与选择器可用性联动、离开重入后的默认态恢复。
- **契约与元数据层**：覆盖 `@tc.number` 编号、用例命名、组件 id、资源键与 `BLANK` 占位符契约。

### 2.2 高复用设计

测试通过以下方式降低维护成本：

- **统一套件注册**：`List.test.ets` 统一 import 并调用 24 个套件入口，按固定顺序执行，便于审计与按类回归。
- **共享测试驱动**：`shared/AudioDriver.ets` 统一封装 `Driver.create()` 单例、`ensureHomeReady`、`openFromHome`、`tapId`、`exists`、`getSubtreeText`、`labelOf`/`stringsOf` 等能力，套件只写断言。
- **统一环境常量**：`BUNDLE_NAME = 'com.samples.audio'`、首页标记 `select_output_device_card`、`PAGE_TIMEOUT`、`ANIMATION_SETTLE` 在各套件中保持一致。
- **统一数据构造**：内容类型/流用途通过 `CONTENT_TYPES`、`STREAM_USAGES` 表统一驱动；页面选择项优先按资源文案定位，而非硬编码坐标。
- **统一断言风格**：核心交互/状态用例至少覆盖 2–3 个针对性断言（返回值、状态、id 切换、副作用），导航与资源接线类以 1–2 条针对性断言为主。

### 2.3 矩阵化设计

关键路径采用组合矩阵扩展覆盖：

- **音效选择矩阵**：内容类型（6）× 流用途（15）× 音效模式（直通/默认），在预置与实时两个页面验证选择回显、互不影响、查询结果重置。
- **采集模式矩阵**：Normal / Live / Parallel 三标签 × 空闲/录制态 × 往返切换/重入复位。
- **页面矩阵**：首页七个入口 × 打开/返回/重入 × 标记控件消失与首页恢复。
- **录制状态矩阵**：开始 → 暂停 → 继续 → 停止 × 计时格式与控件集合。
- **焦点矩阵**：音乐/铃声两个播放器的空闲、播放、停止与互相影响。
- **资源矩阵**：页面标题、内容类型、流用途、音效模式、卡拉 OK 状态、按钮、设备类型、混响/均衡器文案。

矩阵只用于真实边界和分支组合，不通过复制用例体或重复命名放大数量。

## 3. 测试对象拆解

### 3.1 主流程

- **应用承载**：`entryability/EntryAbility.ts` 负责启动与麦克风授权，随后加载首页。
- **页面与交互**：
  - `pages/Index.ets`：首页，暴露发声设备、音频焦点、音效管理、音频录制、音量面板、空间音频、卡拉 OK 七个入口。
  - `pages/PreferOutputDevice.ets`：查询并展示当前首选输出设备类型名称。
  - `pages/Focus.ets`：音乐/铃声两个播放器的播放、停止与音频焦点交互。
  - `pages/PresetEffect.ets` / `pages/RealtimeEffect.ets`：内容类型、流用途、音效模式选择与查询；实时页还包含播放/暂停与选择器置灰。
  - `pages/NormalCapturer.ets` / `pages/LiveCapturer.ets` / `pages/ParallelCapturer.ets`：普通/实时/并行录制，含计时与播放卡片。
  - `pages/VolumePanel.ets`：音量加减。
  - `pages/SpatialAudio.ets`：2.0/5.1 音轨播放与空间音频支持态。
  - `pages/Karaoke.ets`：耳返初始化/开启/关闭、音量、混响与均衡器。
- **系统能力**：`@ohos.multimedia.audio` 的 AudioRenderer、AudioLoopback、AudioRoutingManager、AudioSpatializationManager，以及 `resourceManager` 资源读取。

### 3.2 关键风险

- 麦克风权限未授予时，录制与部分音频用例不可用；首页也会被权限弹窗拦截。
- 无音频输出/采集设备或设备不支持空间音频、耳返时，相关页面进入不支持态。
- UI 渲染时序差异会导致固定延时后仍找不到控件，需以 `waitForComponent` 轮询而非固定 sleep。
- UiTest 每进程仅允许一个 Driver，且要求被测应用处于前台；套件需通过 `ensureHomeReady` 统一切回首页。
- 播放态与选择器可用性强相关：播放中内容/用途选择器应置灰，暂停后恢复。
- 选择项较多时（15 项流用途）下拉列表需要滚动，屏幕外选项不可直接点击。
- 资源键缺失或未接线时，页面文案会显示为空或原始键名。
- 录制时长、计时进位、停止阈值等时间相关行为存在调度误差。

## 4. 覆盖维度设计

### 4.1 功能正确性

- 应用启动、首页七个入口展示与跳转、页面返回与重入。
- 发声设备名称解析、音频焦点两播放器的播放/停止。
- 预置/实时音效的内容类型、流用途、模式选择与查询结果。
- 采集器三标签页起始控件、Normal/Live/Parallel 录制状态机与计时格式。
- 音量加减、空间音频 2.0/5.1 播放切换、卡拉 OK 初始化/开关/音效文案。

### 4.2 边界与异常

- 选择项：默认值（UNKNOWN/UNKNOWN/DEFAULT）、切换到非默认项、再切回默认项。
- 状态：播放中置灰、暂停后恢复；离开页面后计时/控件复位。
- 导航：首页→子页→返回→再进入；连续跨两页操作后仍回到首页。
- 资源：缺失键拒绝、`BLANK` 解析为 `--`、KTV 等“值等于键名”的合法资源。
- 采集：空闲态仅显示开始控件，录制/暂停/继续/停止的控件互斥。

### 4.3 契约与数据

- `@tc.number`、`@tc.name`、`@tc.desc`、`@tc.size`、`@tc.type`、`@tc.level` 全量存在。
- `@tc.number` 按套件内 `0100/0200/0300…` 递增，全局唯一；`@tc.name` 与 `it()` 名称一致。
- 组件 id 契约：首页卡片、各页面选择器/播放控件/返回入口、录制控件命名稳定。
- 资源键契约：内容类型 6 项、流用途 15 项、音效 3 项、卡拉 OK 状态 9 项均可解析。

### 4.4 稳定性与隔离

- 每个 UI 套件在 `beforeAll` 执行 `ensureHomeReady`，用例前通过 `openFromHome` 统一切回首页，避免跨套件残留页面。
- 导航类用例采用 `waitForComponent` 轮询 + `pressBack`，不依赖固定坐标。
- 页面重入用例显式验证“返回后首页可见、子页标记消失”，避免状态串扰。
- 资源用例不依赖设备 UI，执行快、可重复；UI 用例按页面分组，失败可按 `class + testName` 定位。

### 4.5 可维护性

- 套件按“导航/重入、内容页交互、录制链路、音频焦点、资源/生命周期、章节综合”分组。
- 新增边界优先追加到对应主题套件，不修改既有编号与用例名。
- 选择项与资源文案统一通过 `labelOf`/`stringsOf` 获取，避免硬编码中英文。

## 5. 充分性说明

### 5.1 为什么认为当前测试具备较强充分性

- **覆盖层次完整**：从应用启动、首页导航，到各功能页交互、录制状态机、资源接线与重入稳定性均有覆盖。
- **覆盖方式多样**：包含真实 UiTest 操作、资源解析、状态机、选择矩阵、重复进入与跨页顺序。
- **数量与质量同时约束**：218 条用例名称与编号全部唯一，核心交互用例具备明确的前置、操作与后置断言。
- **断言可定位**：同时校验可见性、控件 id 切换、选择文本、状态文本与返回后首页恢复，而非只验证“接口存在”。
- **矩阵可审计**：选择项、标签页、页面入口、资源键均可独立复核。

### 5.2 数量与质量门禁

| 指标 | 当前值 |

| 用例总数 | 218 |

### 5.3 运行与限制

- 运行前需唤醒并解锁设备，并授予麦克风权限；权限弹窗会阻塞首页加载。
- 建议执行 `power-shell timeout -o 600000` 延长息屏时间，避免长时间串行执行中断。
- UiTest 每进程仅允许一个 Driver，且只能看到当前前台窗口；套件通过 `ensureHomeReady` 统一切回首页。
- 空间音频、耳返（AudioLoopback）、音频渲染器依赖设备能力；不支持时页面进入不支持态，相关断言只校验可观察状态。
- 流用途下拉为 15 项滚动列表，屏幕外选项无法直接点击，用例选择列表顶部可见项进行验证。
- 真实音频听感、音画同步、编码质量不在自动化断言范围内，由手工用例保障。

## 7. 结论

`Audio` 当前测试已经形成“真实 UiTest 交互 + 录制状态机 + 选择矩阵 + 资源接线 + 重入稳定性”的组合式覆盖结构。该结构具备明确的导航前置、可复现的设备依赖说明、唯一的用例编号和较完整的选择/状态组合，可作为后续版本回归、接口变更审计和测试扩展的基础。

后续扩展应优先补充真实录制链路（普通/实时/并行的完整录制与播放）、空间音频 5.1 与耳返在不支持设备上的降级路径，以及更多资源/国际化组合；新增用例需继续保持唯一名称与编号，并优先复现真实业务分支，而不是重复矩阵放大数量。

## 断言真实性说明

- 运行时探针确认 `Driver.waitForComponent`/`findComponent` 未命中返回 `null`（不是 `undefined`），测试统一使用 `exists`/`openFromHome` 做存在性判断。
