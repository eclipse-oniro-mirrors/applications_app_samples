# 全部应用测试说明

> 本说明面向 `TVApplicationManager`（TV 形态全部应用）工程，用于说明全部应用的测试设计思路、覆盖维度与充分性依据。

## 1. 文档目标

本文档用于说明 `TVApplicationManager` 自动化测试的设计思路、覆盖维度、充分性依据与后续扩展方向。文档聚焦"为什么这样设计测试"和"当前测试为何具备较强覆盖能力"，用于辅助代码评审、测试审计和后续扩展。

## 2. 测试设计原则

### 2.1 分层设计

测试按以下层次拆分，避免所有用例堆叠在单一场景层：

- Foundation 层：以 `product/tv/src/ohosTest/ets/test/common/SharedDriver.ets` 为核心，提供串行化 UI 操作执行器、遥控器按键/触摸模拟、焦点与组件断言、超时/容差常量与 Driver 管理
- Domain 层：围绕应用列表数据与算法、网格焦点算法、菜单弹窗状态机、缓存/节流/过滤等核心域逻辑展开确定性单元测试（含 `integration/RealModule.test.ets` 的主代码逻辑副本）
- Scene 层：模拟权限流、主界面渲染、焦点导航、菜单弹窗、应用操作流、恢复场景、用户场景等真实 TV 使用场景
- Quality 层：补充性能、长稳压力、并发、内存泄漏、安全、契约、无障碍、配置兼容性等非功能维度

这一分层设计确保测试既能覆盖基础行为正确性，也能覆盖复杂交互与质量属性。

### 2.2 高复用设计

测试中大量复用以下设计资产：

- `common/SharedDriver.ets`：57 个测试文件复用，提供 `runSerializedUiOperation`、`triggerSerializedKey`、`pressAndWait`、`triggerMenuDialog`、`simulateTouch`、`checkFocusState`、`checkTextContent`、`appComponentCount`、`waitForUiStable` 等能力，并统一定义遥控器键码（KEY_LEFT/RIGHT/UP/DOWN/ENTER/BACK/HOME/MENU）与超时、容差常量
- 文件级单例 Tracker 模式：每个测试文件自带 `XxxTracker.getInstance()` 单例，既模拟业务状态又记录操作历史与统计
- `integration/RealModule.test.ets`：直接复制主代码真实逻辑（`Throttle`、`MemoryCache`、`Index.getAppInfo`、`FilterAppList`、分批加载）作为确定性单元测试的基准

通过复用驱动、Tracker 和逻辑副本，避免重复造轮子，使测试更容易扩展到更深的参数矩阵和更长的回归链路。

### 2.3 矩阵化设计

关键场景不只测试单点，而是采用组合矩阵扩展覆盖：

- 分辨率 × 语言 × 方向（`configuration/DeviceCompatibility.test.ets`）
- 输入方向 × 焦点位置（`uiInteraction/GridFocusNavigation.test.ets`）
- 生命周期状态 × 故障模式（`lifecycle/AbilitySessionManagement.test.ets`、`errorHandling/ErrorRecovery.test.ets`、`menuDialog/MenuDialogStateManagement.test.ets`）
- SDK 版本 × 分辨率、平板 × 读屏（`configuration/Compatibility.test.ets`）
- 语言 × 主题 × 字体大小变更组合（`configuration/ConfigurationChanges.test.ets`）
- 弹窗位置五锚点矩阵（`menuDialog/MenuDialogPositioning.test.ets`）
- 主题 / 缩放 / 语言枚举矩阵（`configuration/ThemeVariation.test.ets`、`ContentScaling.test.ets`、`LocalizationTesting.test.ets`）
- 网络状态 × 中断场景组合（`network/InterruptNetwork.test.ets`）

矩阵化设计的意义在于降低"单点通过、组合失败"的漏测风险。

## 3. 测试对象拆解

### 3.1 主流程

主流程测试聚焦以下对象：

- 应用列表获取、过滤、排序与去重（`pages/Index.ets` 的 `getAppInfo`、`components/FilterApp.ets`）
- 网格布局与分批加载（`view/GridList.ets`，6 列 × 3 行首屏 18 个 + 每批 6 个）
- 网格焦点算法（`common/utils/AppListUtil.ets` 的 `moveFocusUp/Down/Left/Right`、`judgeDirection`、`getPlacement` 等）
- 菜单弹窗（`components/CustomDialog.ets`：卸载、移动、添加快捷方式）
- 应用启动、卸载、移动、快捷方式完整操作流
- 图标与名称缓存（`Utils/AppIconCacheManager.ets`、`AppNameCacheManager.ets`、`MemoryCache.ets`、`DiskCache.ets`）
- 排序持久化（`common/utils/Storage.ets`）
- 事件与节流（`common/utils/EventUtil.ets`、`Throttle.ets`、emitter 事件链路）

### 3.2 关键风险点

围绕 TV 应用管理场景，重点识别如下风险：

- 应用列表数据量波动或安装/卸载变化导致布局与渲染退化
- 焦点导航越界、焦点丢失或方向循环失效
- 菜单弹窗并发/快速开关导致状态污染
- 卸载、移动、快捷方式操作与列表状态不同步
- 后台恢复、配置变更、网络中断后列表与缓存残留脏数据
- 系统应用误操作、敏感数据泄露、权限缺失导致安全问题
- 无障碍树缺失、文本不可读或焦点无法按遥控方向导航
- 多语言、主题、缩放、分辨率组合下布局越界或渲染异常

这些风险点直接决定了当前测试设计的重点方向。

## 4. 覆盖维度设计

### 4.1 功能正确性

功能测试不只验证"能否管理应用"，而是拆成可验证的细粒度行为：

- 应用列表渲染与分批加载
- 方向键焦点移动与循环
- 菜单弹窗打开、关闭与状态转换
- 启动应用
- 卸载应用
- 移动应用（交换位置）
- 添加到桌面快捷方式
- 排序持久化写入与恢复
- 前后台切换列表刷新

这样可以定位失败点，而不是只得到"主流程失败"的粗粒度结论。

### 4.2 异常流与恢复

异常流设计覆盖：

- 启动失败
- 卸载失败与错误码映射
- 资源加载失败（图标/名称）
- 超时与无效输入
- 空引用与无效状态
- 焦点丢失与组件渲染失败
- 配置变更、网络中断期间的异常处理

恢复类测试要求不仅校验接口返回值，还要求校验：

- 当前焦点是否回归有效位置
- 网格组件数量是否回到稳定基线（容差 `TOLERANCE_COMPONENT_COUNT = 3`）
- 弹窗状态机是否回到合法状态
- 列表与缓存数据是否一致、是否存在污染

这保证了异常测试不仅关注"报错"，也关注"报错之后系统是否恢复正确"。

### 4.3 并发与长稳

TV 形态下，用户可能连续执行导航、开窗、关窗、切换焦点等动作，因此需要覆盖：

- 并发按键与并发操作（`concurrency/ConcurrencyControl.test.ets`）
- 并发任务调度与取消（`concurrency/AppConcurrency.test.ets`）
- 高频导航与快速焦点变化
- 长轮次混合操作回放（`performance/LongTermStability.test.ets`、`PerformanceStress.test.ets`）
- 弹窗开关与导航后的内存泄漏检测（`performance/MemoryLeakDetection.test.ets`）
- 组件数双遍比对与计数稳定性校验

长稳测试采用混合动作回放，而不是单一动作重复，以更贴近真实使用路径。

### 4.4 性能与兼容性

性能设计不只关注单个耗时值，而是通过以下方式提升充分性：

- 记录焦点切换、菜单弹窗、操作执行、页面渲染多类时延
- 使用平均值、峰值、最大/最小值和限时断言（500ms 焦点、2000ms 操作、5000ms 渲染等）观察趋势
- 对同一操作序列做双遍组件数与耗时指纹比对，验证稳定性
- 在 75%~200% 缩放、多种分辨率、多语言、多主题下重复执行

兼容性设计强调多维组合，避免只在默认环境通过。

### 4.5 安全与契约

安全与契约测试设计包含：

- 功能与权限映射完整性检查（`security/AppPermission.test.ets`、`AppPermissionValidation.test.ets`）
- 系统权限要求、拒绝降级与撤销重授权（`security/SecurityPermission.test.ets`）
- 敏感数据保护（手机号、身份证掩码等）
- 操作目录契约（`appManagement/AppOperationCatalog.test.ets`：操作 ID 唯一性、驼峰命名、语义完整性）
- 快捷方式公共事件契约（`appManagement/ShortcutCommonEventValidation.test.ets`：订阅/退订、分发、载荷）
- 读屏模式下的权限控制与文本可读（`security/SecurityScreenReader.test.ets`）

这一部分用于降低未来版本演进过程中的接口漂移和数据污染风险。

### 4.6 可达性与易用性

针对 TV 端操作特点，测试设计特别覆盖：

- 无障碍读屏焦点导航与焦点顺序逻辑（`security/ScreenReaderNavigation.test.ets`）
- 关键文案是否可读、高对比度兼容
- 焦点高亮样式与焦点变化反馈（`uiInteraction/AppFocusHighlight.test.ets`）
- 弹窗五锚点定位精度（`menuDialog/MenuDialogPositioning.test.ets`）
- 布局在不同分辨率、字体缩放下是否越界（`animationVisual/UIVisual.test.ets`）

这部分是判断 TV 大屏可用性的重要补充。

## 5. 充分性说明

### 5.1 为什么认为当前测试具备较强充分性

当前测试充分性主要来自以下几个方面：

- 覆盖层次完整：从公共驱动层到单元算法层、场景回归层与质量层都有对应测试
- 覆盖维度：功能、异常、并发、性能、安全、契约、无障碍、兼容性均已纳入
- 覆盖方式多样：单点验证、矩阵组合、长稳回放、双遍指纹、状态快照并存
- 数据校验细化：不仅校验操作结果，还校验焦点、组件数、状态机、列表与缓存数据
- 测试资产可复用：SharedDriver 与文件级 Tracker 模式便于继续扩展而不破坏既有结构

## 6. 当前测试目录与职责

| 目录 | 职责 |
|---|---|
| animationVisual | 动画与视觉表现测试（动画控制器、视觉渲染、焦点环） |
| appList | 应用列表数据、算法、渲染、持久化与恢复测试 |
| appManagement | 应用管理操作测试（启动、卸载、移动、快捷方式、导航） |
| concurrency | 并发任务调度与并发控制测试 |
| configuration | 配置、兼容性与多维度适配测试（分辨率、语言、主题、缩放） |
| errorHandling | 异常流、边界与错误恢复测试 |
| integration | 系统集成、真实模块逻辑副本与用户场景测试 |
| lifecycle | Ability 生命周期与会话管理测试 |
| logging | 日志系统测试 |
| menuDialog | 菜单弹窗生命周期、状态管理与定位测试 |
| network | 网络连通性与中断场景测试 |
| performance | 性能、长稳、压力与内存泄漏检测测试 |
| security | 权限、安全与无障碍测试 |
| uiInteraction | UI 交互测试（焦点、按键、触摸、手势、事件） |

## 7. 结论

`TVApplicationManager` 当前测试设计已经形成"基础设施 + 核心域 + 真实场景 + 非功能质量"的组合式覆盖结构。该结构具备良好的扩展性、可维护性和风险发现能力，可以作为全部应用后续持续集成、版本回归和测试审计的核心基础。
